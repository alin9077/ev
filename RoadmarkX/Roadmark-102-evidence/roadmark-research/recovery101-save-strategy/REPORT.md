# Small frequent durable saves for reimplemented101

## Recommendation

Keep the six restored checkpoint100 artifacts as the immutable durable base. During reimplementation, create small cumulative work-in-progress recovery capsules, each independently restorable from checkpoint100 plus that one capsule. Do not wait for final QA to save recoverable source, and do not call a WIP capsule an accepted checkpoint101.

Save at these concrete boundaries:

1. As soon as the new101 candidate, complete changed/new files, maps and recovery instructions exist, before application or long QA
2. Immediately after independent review and exact root application, before test/build/browser work
3. After each completed long validation phase or meaningful new review/fix, carrying the cumulative source and actual available evidence
4. Before any deliberate pause, environment transition or long operation that could leave the latest source unsaved
5. After final acceptance, produce the normal complete source parts/kit, preview and research package

A save is durable only after the supported Library create flow returns an actual successful new identity. A local ZIP, worker completion, progress message or upload request is insufficient. Send the confirmed new capsule as a native attachment and retain a short actual receipt in chat: filename, Library ID, version, byte count, local SHA and clear WIP status. Never claim independent server-byte verification from local hashing. When supported, a newly materialized saved copy can be independently checked through the official Library route.

## Minimal capsule contents

- A manifest naming the exact checkpoint100 source SHA,48,765,019-byte size and the three-part/recovery-kit dependency; the saved100 preview identity stays separate
- A complete baseline input map and complete current expected map, preserving original serialization while comparing map semantics where appropriate
- Full current bytes for every changed/new application file relative to100, including generated data, fixtures, helpers, tests and docs; explicit add/modify/delete operations, before/after hashes and lengths; no silent deletions
- For modified paths, exact baseline preimage hashes and optionally small preimage bytes; the immutable source100 archive remains the authoritative preimage source
- Current candidate/review/recovery-tooling files and bounded actual logs/results needed to resume, including incomplete/failed attempts honestly labeled; never fabricate process exits after a reset
- Short restore instructions and `work_in_progress_unaccepted` status; individual QA/browser/artifact/acceptance stages remain pending or reflect only supplied actual evidence
- Prior durable-capsule receipt and current selected-file inventory; exclude secrets, raw publisher bodies, credentials, screenshots and unrelated private material

Every capsule should be cumulative from100, not dependent on an unbounded chain of earlier WIP patches. This normally makes one small ZIP sufficient. Measure actual bytes; require it below32MiB. If evidence grows too large, keep the source capsule small and separately save a clearly indexed evidence ZIP, with exact identities and no omitted source dependency. Avoid resaving the unchanged48.8MB source and16.4MB preview at every step.

## Verify before saving

Use an explicitly reviewed small packager/checker with exclusive output paths. It need not run the app or wait for QA. It must verify the exact100 baseline identity, safe paths/no symlinks, every selected file hash/length, exact ZIP member readback and source-map completeness. Independently simulate restoration in memory or a disposable external directory from100 plus the capsule and verify the whole expected input map, preserving all historical source outside the allowlist. Do not regenerate files during restore to hide missing artifacts. App execution is separate.

Only then perform new-create Library saves under the user's authorization. Preserve all old artifacts and never update/delete prior IDs. Retain actual helper results and handle partial or uncertain outcomes without blind retry. Since an artifact cannot contain its own as-yet-unknown upload result, preserve that result in chat immediately and carry it into the next capsule. Final full-package recovery still needs actual shipped-joiner reconstruction and complete final review; a WIP capsule does not weaken those gates.
