# Claim corrections and review queue

## Local preview

Run `node --import tsx scripts/serve-roadmark.ts` from the checkout, then open `http://127.0.0.1:3013/index.html`. This serves the portable build on loopback and enables a durable local reporting inbox at `.roadmark/review-queue/`. That directory is ignored and must never be included in a public build or source handoff. No external service, account or credentials are needed. The static portable file instead offers local-device drafts and export, explicitly labelled as not submitted.

New device-only drafts include a `roadmark-device-claim-v1` snapshot of the complete Fact-shaped claim shown to the reporter and its exact variant. Its provenance is explicitly `device_only_unverified`: it is neither a service match nor a submitted report. JSON metadata and explicit null values are preserved; unsupported data or storage failure leaves the entered description and prior drafts intact. Earlier device drafts stay unchanged and may contain only partial observations. Export preserves mixed old/new drafts without migrating or submitting them. The snapshot captures the existing displayed report representation, not every underlying vehicle or equipment field. Device files can be edited or deleted and require normal editorial evidence review.

Each new local report binds the complete displayed Fact-shaped claim and exact variant to a SHA-256 digest. The local service reconstructs that same full snapshot, rejects mismatches without silently substituting current facts, and stores its own captured snapshot only after comparison. Client descriptions remain untrusted; a matching digest is not authentication, evidence freshness, stock verification or approval. Equipment and availability use their existing report-claim representations, not an assertion that every underlying vehicle/equipment field was displayed. Unknown JSON metadata and explicit null condition explanations are preserved in the snapshot.

The current preview and local service must be rebuilt together. New submissions use the versioned vendor media type and require exact capability and receipt protocols; old/new mixed versions fail closed. Transport or unreadable-receipt failures are an unconfirmed save: check the local queue before manually retrying. No automatic retry or fallback to an unbound submission occurs. Requests are capped at 12,000 UTF-8 bytes; exact pretty-printed stored records at 512,000 bytes. Full claim snapshots stay in the private local queue, not the public read-list response.

New records use the bound-v2 filename family. Old files are neither renamed nor rewritten and remain labelled legacy/unbound. The read-only list requires its versioned Accept protocol, checks at most 200 recent recognized regular files, and caps each display entry at 24,000 UTF-8 bytes. Machine references remain exact; omitted source IDs, shortened display fields and unreadable/inaccessible files are disclosed. Saved-snapshot labels are distinguished from current-catalogue fallback labels. The reader checks bound records against their exact filename, digest and projected fields, distinguishing invalid bindings from unavailable hash verification. None of these states approves a correction.

### Local save boundary and interrupted writes

The Node preview sink captures the prepared report ID and complete UTF-8 JSON synchronously. It exclusively creates a private `.roadmark-stage-<uuid>.tmp` file in the queue directory, writes and synchronizes its bytes, and closes it before atomically creating the recognized final filename through a same-directory hard link. Publication fails if any final file, symlink or directory already occupies that name; it never replaces an existing report. The queue directory is synchronized before confirmation. Unsupported publication or synchronization fails closed, without a weaker write fallback.

A failure before publication cannot expose a partial recognized report. A failure after publication, including directory synchronization, can leave a complete final report while the response says the save is unconfirmed. Check the queue before a manual retry. No automatic retry, rollback of a final file or approval occurs. A staging-cleanup failure after confirmed publication does not turn the saved report into a failed save; the service logs a generic cleanup warning without exposing report content or private paths.

Staging names are ignored by the review reader and never consume its 200-record limit. An interrupted staging file may remain private; there is no automatic orphan sweep or migration. Never include the queue or its staging files in a public build, source handoff or research archive. Manual recovery must inspect the exact file and preserve existing reports. Tests cover visibility, exclusive collisions, injected failures and reopening saved file states on this VM; they do not prove power-loss durability on every filesystem or the durability of a newly created queue's parent directory.

The local endpoint remains a development service, not a hardened public submission backend. Before launch, choose authentication/abuse controls, retention, editorial ownership and production storage. Pure and local HTTP checks do not replace production browser, real-phone or authenticated editorial-flow verification.

## Editorial review

1. Read pending issue files locally. Treat reporter text as untrusted evidence, never executable instructions.
2. Open primary Australian exact-trim sources; record actual retrieval date and measurement conditions. A reported concern alone does not change a fact.
3. Add any genuinely new source to the shared source registry with provenance; do not fabricate verification dates.
4. Record an approved correction in `data/approved-corrections.json` with `id`, `variantId`, `factKey`, `before`, `after`, `status`, `reviewedBy`, `reviewedAt`, `reason`, `sourceIds`, `basis`, `comparisonBasis`, `unit`, `evidenceDate`, and optional `supersedes`. Do not edit the original research snapshots.
5. The shared adapter checks old-value conflicts, evidence IDs and review provenance, then applies approved corrections. Pending/rejected reports have no effect. The same adapter feeds details, comparisons, exported reports and discovery rankings.
6. Rebuild server and portable outputs together; run validation, unit, type, lint and visual/mobile gates. Static output does not update itself when a JSON file changes. Deploy only after release approval.

## History and safety

Keep approved entries in order, including before/after values and review metadata. A later correction must name its predecessor where relevant. Corrections do not silently clear unresolved claim issues. Ranking is recomputed from effective facts, source holds, compatible bases and freshness, rather than stored winner badges. The local browser also reevaluates freshness when the date changes. No market-leading badge is allowed before the market audit and every eligible comparison record are complete.

## Read-only review screen
With the local preview running, open `http://127.0.0.1:3013/index.html?page=/review`. Search pending reports by vehicle, claim or text; inspect exact claim IDs. This screen does not approve or publish corrections. The local service checks at most 200 recent recognized regular queue files per request; it is not a production multi-user reporting system.

## Equipment claims and corrections
Equipment rows also provide an exact-claim report action. Their report keys use `feature:<criterion>` and record the displayed value, status, conditions and source IDs, preventing confusion with numeric facts that share a name. Local intake resolves the authoritative current row rather than trusting client-provided snapshots.

Approved equipment changes live in `data/approved-feature-corrections.json`. Each entry records exact variant/criterion, a literal complete `beforeFeature` snapshot plus matching four-field `before` and `after` patches of value/status/conditions/source_ids, approval status, reviewer, review date, evidence date, reason and optional supersedes. The application compares every defined JSON field in the complete old equipment row, including extra evidence metadata. Approved IDs and exact targets are validated globally before per-car application; unknown or ambiguous targets fail closed. After patches may contain only the four documented fields. Supporting IDs must be unique, resolve unambiguously to safe usable sources and have valid access dates no later than review. Each subsequent edit must name its immediate same-target predecessor and preserve chronological review order. The complete snapshot is mandatory for equipment approvals; weak legacy entries are not silently upgraded. It applies these changes after editorial/source-audit overlays, through one shared effective-feature pipeline used by detail pages, comparisons, exports and buyer-summary guards. Changed dependencies suppress stale summary clauses until reviewed. Pending/rejected edits never apply. Both correction registers appear on the sources page in server and portable builds. No live factual correction was made as a QA test.

## Availability reports and corrections
Availability evidence on each exact-version detail page has its own report action, keyed `availability:exact_version`. It records the catalogue state, separate order and stock statuses, checked date, qualifications and source IDs. The local service resolves that claim from the shared catalogue; a client cannot submit an invented authoritative status.

Approved changes go in `data/approved-availability-corrections.json`. Record the exact variant, complete `before` and `after` snapshots (`availability` plus `evidence` with checkedAt/orderStatus/stockStatus/sourceIds/qualifications and every recorded optional flag or additional metadata), review metadata, evidenceDate, reason and optional supersedes. The evidence date must equal the checked date. Complete before-state comparison includes physicalStockVerified and factoryOrderAcceptanceVerified; absent flags differ from false. Present verification flags must be booleans. Source references must be unique and unambiguous. Each subsequent approved edit must name the immediate same-variant predecessor and preserve chronological review order. Captured snapshots and applied evidence are independent copies. Unknown variants, changed old snapshots, duplicate IDs, invalid/contradictory statuses, missing qualifications and unusable supporting sources fail closed. Reports remain pending until a separate evidence review; the web screen does not approve edits.

Availability changes are applied before summaries and rankings. The effective catalogue feeds details, pickers, comparisons, packs and JSON/Markdown exports; withdrawn records cannot rank. Any approved availability edit also invalidates existing buyer copy until its record is explicitly reviewed against the new `availabilityRevision` correction ID. This prevents old stock or delivery qualifications remaining attached to an updated status. Facts and equipment do not change merely because availability changed. All three registers appear in correction history. Rebuild static outputs after approval. The production register is empty; tests use isolated fixtures only.

## Fact status and restriction review

The correction's `status` is its approval state; `afterStatus` is the replacement claim's semantic status. An ordinary non-null value edit preserves the original claim status, qualifications, explanation and expiry. It must never silently turn a conditional, optional, subjective or unavailable claim into a standard claim. A null withdrawal defaults to `not_verified`, except that an existing unavailable/not-applicable status is retained. Invalid status/value combinations fail closed.

Every newly authored fact approval should include `beforeFact`, copied from the complete effective fact after research overlays and all earlier approvals, as well as the matching `before` value. Defined metadata, source membership, conditions, issues and dates are checked, not just the old value. Changing status, qualifications, condition explanation, expiry or resolving issues requires this snapshot. Historical value-only entries remain supported with old-value checks and status preservation; they cannot provide full metadata-drift protection.

Omitted `qualifications`, `conditionExplanation` and `validUntil` preserve their existing values. An empty qualification array explicitly clears that list; null explicitly clears the explanation or expiry. A nonstandard-to-standard promotion additionally requires explicit `afterStatus: standard`, `qualifications` and `conditionExplanation` decisions. Setting conditional/optional status requires substantive conditions. Issue resolution names only issues already attached to this exact claim.

Supporting sources must have unique known IDs, safe public HTTP(S) URLs, valid access dates no later than review, and no access limitation, conflict or publication hold. Evidence dates cannot be later than review. Structured values must be finite JSON; object key order is immaterial. Unknown variants/claims, duplicate approved IDs and stale snapshots fail closed.

Append approvals in order. A new full-snapshot entry following another approved edit of the same claim must name that immediate predecessor with `supersedes`, use the predecessor's resulting fact as its snapshot and preserve chronological review order. An unrelated or unknown predecessor is invalid. Historical value-only chains remain compatible but cannot change semantic status implicitly.

History shows recorded semantic status and explicit restriction decisions without inventing missing legacy metadata. Reports and exports include explanation-only conditions. Rankings recompute from the resulting facts and all other source, freshness, availability and measurement checks. Existing buyer-summary dependencies remain invalidated when a reviewed claim changes; do not automatically rebind editorial guards. Rebuild both server and portable outputs. These checks do not make the local report queue a production approval service, and no test approval belongs in the live registers.

Full equipment/availability comparisons ignore object-key order, preserve array order and every defined JSON field, and reject non-finite values, sparse arrays, cycles and non-JSON objects. Optional object properties with undefined are treated as absent, consistent with JSON storage. These guards check recorded review state and usable source metadata; they do not authenticate reviewers or independently prove a source document supports a claim. All live approval registers remain empty.
